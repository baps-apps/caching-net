> **This review supersedes every earlier audit in this directory.** It was conducted from scratch
> against the implementation and against real runtime behaviour, treating prior review conclusions,
> existing tests, README claims and architecture notes as unverified. It found a release blocker that
> all three earlier reviews passed over, so their verdicts should be read as the record of what was
> known at the time rather than as current gate evidence.

## 1. Why the earlier reviews missed the blocker

Every earlier review — and all 441 tests — asserted tag invalidation from a **cold** reader: an
instance that had not yet read the key. A cold reader fetches the invalidation marker from Redis and
therefore sees it. Under real traffic every instance is warm. The defect was invisible to the entire
existing test suite by construction, not by oversight in any single test.

This is the durable lesson from this gate: *a distributed-invalidation test that does not warm the
reader is not testing invalidation.*

## 2. Release blocker — found, fixed, re-verified

**Tag and `Clear` invalidation was silently lost across instances in `Redis` mode, and unbounded in
`Hybrid` without a backplane.**

`RemoveByTag` and `Clear` are implemented as *marker* entries that every read compares itself
against. Markers are configured by `FusionCacheOptions.TagsDefaultEntryOptions` — a **different**
option group from `DefaultEntryOptions`, which was the only one Caching.NET mapped the cache mode
onto. Confirmed by reflection against the engine assembly: markers defaulted to
`Duration = 10 days`, `MemoryCacheDuration = null`, `SkipMemoryCacheRead/Write = false`.

Consequences:

- **`Redis` mode.** Entries bypassed the memory layer; markers did not. An instance's first read
  cached "no marker exists" locally for ten days, and Redis mode registers no backplane, so nothing
  could ever evict it. **Measured: a warm reader still served a tag-invalidated value after 45 s.**
- **`Hybrid` without a backplane.** Markers ignored `Entry.LocalExpiration`, so the documented
  convergence bound held for an overwrite but not for a tag invalidation.

Fixed in `Internal/CacheEngineFactory.MapTagsEntryOptions`, which applies the mode to markers as
well. Seven tests added, all of which fail against the previous code; independently re-verified by a
probe harness outside the repository's own suite. After the fix, Redis invalidation is immediate and
Hybrid-without-backplane converges in 1.5 s rather than >45 s.

**Alternatives considered and rejected:** bounding the marker's local lifetime (weakens Redis mode's
contract to "authoritative within *N*"); enabling a backplane in Redis mode (leaves an unbounded
worst case when a notification is lost); adding a `DisableTagging` opt-out (new public API at a
release gate, deserves its own review cycle). Strict correctness was chosen because Redis mode
already trades latency for consistency on every read, and a silent ten-day staleness window is not an
acceptable default.

## 3. Further defects fixed

- **Flaky chaos test asserting an unguaranteed absolute negative.**
  `RedisOutage_DoesNotProduceBackplaneErrors_BecauseNoPublishIsAttempted` failed intermittently with
  `RedisConnectionException` where only `CircuitBreakerOpen` was allowed. Root cause: with
  `AllowBackgroundDistributedOperations` on (the production default) the L2 write and the backplane
  publish are dispatched as background work, so the write can land while the socket dies — the test
  asserted a property the default does not guarantee. Rewritten to await the distributed write and
  assert on the operation dimension; `TELEMETRY.md`'s matching claim that a publish is "never
  attempted" was corrected.
- **The public-API baseline was blind to method generic parameters.** `PublicApiSurface` rendered a
  method by name only, so `CacheKey.For<T>(object)` was recorded as `For(System.Object id)`.
  Changing `For<T>` to `For<T, TId>` produced an identical baseline and passed the gate, despite
  being source-breaking for every caller. Found because `CacheKey.For(42)` failed to compile in the
  external consumer app while the baseline claimed that signature. Fixed; the regenerated baseline
  differs only by the `<T>` annotations it was previously blind to, which is itself the proof that no
  shipped API changed.

## 4. Redis capacity, re-baselined

The correctness fix costs Redis-mode read latency. `RedisBenchmarks` gained tagged-read rows for both
Redis and Hybrid so the cost stays measured by the repository's own suite, and was re-run in full.

| Method | Mean | vs. pre-fix | Allocated |
|---|---:|---:|---:|
| Hybrid L1 hit | 421.8 ns | 410.4 ns → ×1.03 | 624 B |
| Hybrid L1 hit, 2 tags | 740.6 ns | new row | 1,232 B |
| Redis mode **miss** | 109.6 µs | 107.9 µs → ×1.02 | 3.02 KB |
| Hybrid full miss + factory | 135.5 µs | 129.6 µs → ×1.05 | 13.5 KB |
| Redis mode **hit** | 338.1 µs | 109.1 µs → **×3.10** | 12.2 KB |
| Redis mode hit, 2 tags | 537.0 µs | **×4.92** | 19.0 KB |

**A read that misses is not amplified.** With no entry present there is nothing a marker could
invalidate, so no marker is fetched. The multiplier therefore tracks the *hit* ratio, not the request
rate:

```text
commands ≈ requests × (1 + hitRatio × (2 + tagsPerEntry))
```

At a 95% hit ratio with two tags, 10 000 reads/s becomes ≈48 000 Redis commands/s; the same traffic
at a 20% hit ratio becomes ≈18 000. Guidance published in
[OPERATIONS §4](../OPERATIONS.md#4-capacity) with a matching runbook entry, because the symptom an
operator sees — Redis command rate rising *as the hit ratio improves* — is the opposite of the usual
intuition.

The benchmark independently confirms the command model without counting commands: a miss is known to
be exactly one command at 109.6 µs, so one loopback command is ≈110 µs; dividing the other rows by
that recovers 3.08 and 4.90 against 3 and 5 expected.

Note the resulting inversion: **a Redis-mode hit is now three times dearer than a Redis-mode miss**,
and dearer than a full Hybrid miss that runs a factory.

**On the validity of the cross-session comparison.** The pre-fix and post-fix readings come from
different benchmark sessions, and `BENCHMARKS.md` documents 2× drift between sessions on this
machine. Two rows untouched by the fix act as controls: Redis mode miss moved +1.6% and Hybrid full
miss + factory +4.5% between the two sessions, both inside their own error bars. The machine did not
move, so the hit row's ×3.10 is the fix rather than drift. The ±6.3% error on the post-fix reading
leaves the multiplier between ×2.91 and ×3.29.

**A related figure is easy to misread.** Against the pre-v3 `329d8f4` baseline in the
[baseline comparison](../BENCHMARKS.md#baseline-comparison-the-engine-agnostic-contracts-cost), this
row is now +192% — but that is a composite of two opposite-signed changes: the engine-agnostic
contract made it 5.8% *faster* (115,827 → 109,120 ns), and the marker fix then multiplied it ×3.10
(→ 338,110 ns). The controlled cost of the fix is the ×3.10; the +192% is the net against a contract
that no longer exists.

## 5. Documentation corrected against measurement

Six claims were found wrong and corrected, all against a measurement rather than a re-reading:

1. `TELEMETRY.md` — "the backplane publish is never attempted" during an outage (it can be).
2. `BENCHMARKS.md` — the in-memory table was carried over rather than re-measured.
3. `BENCHMARKS.md` — the Redis/Hybrid table predated the marker fix.
4. `README.md` — the stated rationale for rejecting a backplane in Redis mode.
5. `OPERATIONS.md` — `Clear()` was not documented as *not* releasing memory (measured: 100 000
   entries occupied 114 MB, and the managed heap was still 113 MB thirty seconds after `ClearAsync()`).
6. `CHANGELOG.md` — the "Changed" entry said jitter is absolute while the "Fixed" entry and the code
   say it is proportional with an absolute ceiling; the `MessagePack` pin was recorded as 3.1.7 when
   it is 3.1.8; and the baseline-comparison note claimed the Redis hit path was faster than baseline,
   which the marker fix invalidated.

## 7. Release conditions, both discharged

1. **Re-baseline Redis-mode capacity.** Done — §4. The re-baseline also corrected the model by
   establishing that misses are unamplified, replacing a single multiplier with a hit-ratio formula.
2. **Rebuild from `main` at a tag.** Done. The artefact under audit recorded
   `branch="refs/heads/feat/fusion-cache"` at `84c243c` — a commit predating the fix, so that package
   did not contain it. The release package is built from `main` at `v3.0.0`, provenance verified, and
   the packed assembly confirmed to contain `MapTagsEntryOptions`.

Clean-room from the tag: **0 warnings, 441 passed / 0 failed / 0 skipped**, pack succeeded.

## 8. Residual risks and follow-ups

- **Redis-mode command volume.** Measured on loopback. A team already running Redis mode at volume
  should confirm the new command rate against its own cluster rather than these figures.
- **Stampede protection is process-local.** *N* pods can run up to *N* factory executions for a cold
  key. Documented, not fixed.
- **No performance-regression gate in CI.** A ×3 change of this size would not have been caught
  automatically. Recommended follow-up.
- **`ZiggyCreatures.Caching.Fusion.SyntheticTimeoutException` reaches application code.** The last
  engine detail visible to consumers; a Caching.NET-owned timeout exception is the fix.
- **A `DisableTagging` opt-out** would let a Redis-mode service that never tags opt out of the marker
  reads entirely. New public API, so deliberately deferred past this gate.
