### Item 3 — the Hybrid span deliberately omits `cache.layer`

The metric half is met: `caching.net.layer.duration` carries `cache.layer=redis` for an L2 hit,
produced by `InstrumentedDistributedCache`, which genuinely knows which layer it is.

The span half was changed on purpose. `FusionCacheService.ResolveHitLayer()` returns `null` in Hybrid
mode, so the operation span omits `cache.layer` rather than reporting a value it cannot know. The
engine's top-level `Hit` event carries only `Key` and `IsStale`. The per-level event hubs do expose
the level, but they also fire for FusionCache's internal tag and clear-marker lookups — one logical
read was measured producing two extra `MEM Miss` and two extra `DIST Miss` events — so the level
cannot be attributed to the logical operation by counting them.

The alternative was what shipped in earlier drafts: resolve the layer from the cache *mode*, which
tags a Hybrid hit served by Redis as `cache.layer=memory`. That is wrong in exactly the case an
operator investigates — cold instance, post-deploy, post-eviction, short L1 TTL. Reporting nothing
beats reporting a value that is wrong when it matters. `cache.layer` is still emitted for `InMemory`
and `Redis` modes, where it is tautologically correct, and for the factory.

Per-layer truth in Hybrid lives on `caching.net.layer.duration` and on the child `cache.memory.*` /
`cache.redis.*` spans.

### Item 7 — one performance gate missed, accepted by the package owner

| Gate | Threshold | Baseline `329d8f4` | Current | Result |
|---|---|---:|---:|---|
| `GetOrSet` hit, InMemory, telemetry off | ≤2%, zero added allocations | 116.0 ns / 192 B | 133.2 ns / 192 B | **+14.9% — missed**; allocations met |
| `GetOrSet` hit, InMemory, metrics on | ≤10% | 304.4 ns | 153.4 ns | **−49.6%** — met |
| Redis hit | ≤2% | 115,827 ns | 109,120 ns | −5.8% — met |
| Redis miss | ≤2% | 115,913 ns | 107,856 ns | −7.0% — met |
| Hybrid full miss + factory | ≤2% | 138,538 ns | 129,588 ns | −6.5% — met |

The ~17 ns is guard validation, `CacheEntryOverrides` resolution and the span early-exit check now
running on every call through `FusionCacheService`, where the old surface called the engine directly.
Allocations are unchanged, so it is pure CPU.

**Accepted, not fixed**, by explicit decision of the package owner on 2026-08-11. It buys key and tag
guards that are now *enforced* — in v2 they were a documented, unenforceable limitation — and the
shipping default configuration is materially faster than v2: metrics-on dropped ~150 ns because
Task 11 replaced the engine's event-bridge dispatch with direct `RecordHit`/`RecordMiss`. A
default-configured cache is faster today than before this plan; only the telemetry-off path regressed.
Recorded in `CHANGELOG.md` and `docs/BENCHMARKS.md`.

## 4. Known issues carried into the release

1. **`InMemoryBenchmarks.'Factory execution'` at Concurrency=1 cannot be measured on the current
   commit.** BenchmarkDotNet's pilot stage escalates to ~4.2M ops/iteration and never completes
   within 5–10 minutes; it completes in ~2 s on the `329d8f4` baseline and at Concurrency=64. The
   leading theory is the benchmark's own design — it inserts a new never-expiring, never-evicted key
   per invocation into an unbounded `MemoryCache` — and the design is identical on both commits, so
   it is probably not a cache-code regression. **Unresolved.** That row should not be trusted until
   it is.
2. **Benchmark noise on the measurement machine.** `InMemory L1 hit` read 140.8 / 238 / 279.6 /
   288 ns across identical sessions, and `Hybrid L1 hit` read 410 / 870 / 1,040 ns — swings over 2×,
   sometimes in physically impossible directions. Only low-variance back-to-back readings were
   published as comparisons; the in-memory and Hybrid-L1 tables in `docs/BENCHMARKS.md` are marked as
   carried-over snapshots rather than verified comparisons.
3. **The layer-decorator optimisation has no automated gate.** `LayerDecoratorBenchmarks` makes a
   regression visible (reverting the live listener check moves the no-listener arm 18.53 ns →
   48.05 ns), but a benchmark cannot fail a build. This is visibility, not enforcement.
4. **`docs/TELEMETRY.md` documents a dashboard-visible semantics change.** `caching.net.hits` and
   `caching.net.misses` are logical, adapter-owned, one per logical read, with no `cache.layer`
   dimension. Any alert rule that assumed the v2 shape should be re-read against that document.

## 5. Deviations from the plan worth recording

The plan's own risk list flagged four items to verify rather than assume. Three were confirmed as
real problems during execution and fixed; the fourth did not survive contact with measurement:

- **`ConfigurationOptions.CertificateValidation` multicast semantics** — confirmed dangerous. It is a
  field-like event handed verbatim to `SslStream`, so two `+=` subscriptions mean last-wins, and the
  plan's own wiring would have let an application callback returning `true` override Caching.NET's
  certificate rejection. Shipped as a single short-circuiting `&&` with Caching.NET's validator as the
  left operand.
- **Span duration on non-awaited tasks** — confirmed. Every span-bearing verb awaits inside the span
  scope; pinned by a duration assertion that fails if a verb returns the engine's task.
- **`FusionCacheFactoryExecutionContext.Options`** — turned out to be settable, but the code still
  mutates in place, which is the engine's own idiom.
- **`caching.net.hits`/`misses` moving to layer-level probes** — this is the one the plan got wrong.
  Measured, decorator-level counting produced `hits=2, misses=5` for a sequence with 2 logical hits
  and 1 logical miss, because the engine double-probes L1 on a cold read and writes emit internal
  `get` probes. That is a reported hit ratio of 28.6% against a true 66.7%. The counters were moved
  back to logical, adapter-owned semantics; the per-layer breakdown lives on
  `caching.net.layer.duration`, which carries `cache.result` per layer.

## 6. Verdict

**Approved for release.** The engine is absent from the public surface, enforced at three levels: the
approved-API baseline, a reflection test over every public signature, and the `CACHENET001` analyzer
shipped inside the package. All 357 tests pass, including Docker and cross-process suites (391 at
`a02a472` — see the [amendment](#amendment--2026-08-11-after-the-final-review)). The AOT binary runs.

The two spec items not met are both conscious, documented decisions rather than oversights: the
Hybrid span omits a layer tag it cannot determine honestly, and one performance gate was missed and
accepted in exchange for enforced guards and a faster default configuration.

## Amendment — 2026-08-11, after the final review

The gate above was run against `39b8014`. A final review of the source, the tests and the
documentation was then run over the same branch and found **7 Critical and 14 Important** issues
across the three areas, plus a set of minors. All were fixed in `cad7a6b..a02a472` before release.
The original findings above are unchanged; this section records what came after them.

### What changed in the product

| Commit | Change |
|---|---|
| `65056a0` | **Breaking.** `Entry.MemorySizeLimitMegabytes` → `Entry.MemorySizeLimit`, no longer multiplied by 1024 × 1024. `MemoryCacheOptions.SizeLimit` bounds the *summed* per-entry `Size`, not bytes, so with the default `defaultEntrySize: 1` it is an entry-count cap. Measured: 200 entries holding ~78 MB stayed resident under the documented "1 MB" cap. `WithMemorySizeLimit`'s first parameter is now `limit`. A new validator rule rejects a size that charges nothing |
| `0723f14` | New `caching.net.evictions` counter. `caching.net.operations` and `caching.net.invalidations` had double-counted every eviction, removal and overwrite — measured, 5 sets + 5 removes booked 15 operations and 10 invalidations; now 10 and 5. Dashboard-visible |
| `4772c82` | `CACHENET001` now bans only `ZiggyCreatures.Caching.Fusion`, not `StackExchange.Redis` (a consumer may legitimately use the Redis client directly), and catches constructed generics such as `MaybeValue<T>` and `FusionCacheFactoryExecutionContext<T>`, which `IdentifierName`/`QualifiedName` registration alone missed |
| `66f234c` | Health-check registration is idempotent — two caches both calling `WithHealthChecks()` used to throw `Duplicate health checks were registered with the name(s): caching-net` at startup. The consumer's `Action<CachingBuilder>` also no longer runs twice per registration |

The fixes above were then independently re-verified, commit `c59814b`. Every check below was run
against the tree, not read off the fix reports.

| Check | Method | Result |

| Disputed CS8619 finding | Compiled both sample shapes against the real assembly | **The reviewer was half wrong.** Exactly one warning, on the README shape: a non-async lambda returns the `Task` itself, so `Task<Order>` → `Task<Order?>` trips generic invariance, while the migration guide's `async` lambda converts its return *expression* and is clean. README fixed; the migration guide correctly left alone |

Four findings the fixers declined were re-adjudicated. Three stand: the unreachable validator branch
is harmless defence-in-depth, the duplicated benchmark `Concurrency` rows are what
`docs/BENCHMARKS.md` publishes to show hit cost staying flat, and the payload/decompression
asymmetry is bounded by `MaximumDecompressedBytes`, validated against `MaximumPayloadBytes` by
`CachingOptionsValidator`, and documented in five places.

**The fourth was overturned by evidence.** `FindFreeTcpPort`'s time-of-check/time-of-use race was
declined as "more machinery than the flake it removes" — and then
`RedisOutageTests.InitializeAsync` failed on the very next chaos run, with no leftover container to
explain it. Both chaos classes probed for a free port by opening a listener on port 0 and closing it,
and xUnit runs test classes in parallel, so two probes could be handed the same ephemeral port. The
port cannot be Docker-assigned, because these tests restart their container and Docker re-randomises
published ports across stop/start. Fixed in `c59814b` by reserving each port for the test process's
lifetime and retrying on a fresh one; verified by three consecutive full chaos runs, 13/13 each.
