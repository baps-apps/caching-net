## 1. FINAL VERDICT

**APPROVED FOR PRODUCTION WITH KNOWN RISKS**

The engine-hiding architecture holds under adversarial checking, all three modes work from a real
installed package, multi-pod invalidation is proven with two live processes against real Redis, and
396 tests pass in Release with **zero skipped**. Three defects found during this review — one of them

1. **Sustained-load memory behaviour (§30) was NOT VALIDATED.** No leak test over 10k–100k keys was

   figures were independently re-measured and match the published numbers; the distributed figures
   are carried from `docs/BENCHMARKS.md`.

Neither blocks release. Both are stated as residual risks below rather than being absorbed into a

## 3. ARCHITECTURE VERDICT

**PASS.**

FusionCache 2.6.0 is the single cache engine. There is no second engine and no custom L1/L2
orchestration: `AddHybridCache`, `AddMemoryCache`, `AddStackExchangeRedisCache` and `AddFusionCache`
each occur **0** times in `src/`. No custom stampede protection duplicates the engine's — measured,
100 concurrent `GetOrSet` calls on a cold key produced exactly **1** factory execution.

**The consumer injects `ICacheService`.** No engine type appears in the public API. This is enforced
at four independent levels, which is what makes the claim credible rather than aspirational:

1. `PublicApi.approved.txt`, gated by a test that fails on any surface change.
2. A reflection test walking every public signature, including constructed generics.
3. The `CACHENET001` analyzer, shipped inside the package.
4. **New in this review:** the CI external-consumer job now asserts the engine is *not resolvable
   from DI* against a real installed package. Verified live that the assertion can fail — the engine
   assembly loads transitively, so `GetService` returning null is a real result, not a vacuous one.

**Would an engine swap actually be possible?** Yes, and this is the strongest evidence for it:
`Internal/FusionCacheService` is the only type calling an engine operation and
`Internal/CacheEngineFactory` the only type configuring one. A swap is bounded by those two files
plus the layer decorators. The abstraction is 8 verbs × async/sync plus context-free `GetOrSet`
overloads.

**Is the boundary right?** Yes, with one honest cost: consumers cannot reach engine features that
have no Caching.NET equivalent. That is the deliberate trade — the alternative is re-exporting the
engine's surface, which forfeits swappability. The knobs that matter are reachable through
`CachingOptions` and `CacheEntryOverrides`.

**Redis mode's actual mechanism** (the item that most needed a precise answer, since FusionCache has
no native Redis-only mode): `SetSkipMemoryCache(true)` — memory *cache* bypassed for reads and
writes, memory *locker* still active so stampede protection survives. Redis is authoritative. This
matches what the documentation states.

## 6. DISTRIBUTED SYSTEM REVIEW

**Multi-pod invalidation is proven, not inferred.** Two independent `ServiceProvider`s in separate
object graphs, real Redis, real backplane: `Remove` and `RemoveByTag` both propagated from pod A to
pod B's L1. The integration suite additionally launches a **separate OS process** (`Tests.Pod`) to
test backplane behaviour across real process boundaries.

**Stampede protection is PROCESS-LOCAL.** Measured: 100 concurrent same-key `GetOrSet` in one process
→ 1 factory execution. Across pods, each pod's memory locker is independent, so N pods can each run
the factory once for the same cold key. **Do not claim distributed stampede protection.** For most
workloads this is the correct trade; for a genuinely expensive origin it means N concurrent calls at
N pods on a cold key.

**Namespace isolation holds.** `app-a/prod`, `app-a/uat` and `app-b/prod` sharing one Redis: the same
logical key resolved to three distinct values with no collision, and a remove in UAT did **not** evict
PROD. This is the property that lets multiple applications share a Redis cluster.

**Network failure and recovery** are covered by 13 chaos tests against real containers, including
outage, restart, and fail-safe behaviour, plus auto-recovery.

## 8. PERFORMANCE REVIEW

Independently re-measured this session on Apple M4, .NET 10.0.0, Release, BenchmarkDotNet 0.15.8:

| Benchmark | Mean | Ratio | Allocated | Alloc ratio |
|---|---:|---:|---:|---:|
| Hit, telemetry disabled | 135.33 ns | 1.00 | 192 B | 1.00 |
| Hit, metrics enabled, no trace listener | 153.52 ns | 1.13 | 192 B | **1.00** |
| Hit, trace listener attached | 452.61 ns | **3.35** | 1,464 B | **7.62** |
| Miss, telemetry disabled | 89.67 ns | 0.66 | 200 B | 1.04 |
| Miss, metrics enabled, no trace listener | 108.54 ns | 0.80 | 192 B | 1.00 |
| Miss, trace listener attached | 443.80 ns | 3.28 | 1,456 B | 7.58 |

**The published figures are honest.** `docs/BENCHMARKS.md` states 439.0 ns / 3.30× / 1,464 B for a
traced hit; I measured 452.61 ns / 3.35× / **1,464 B** — within noise, allocations identical.

**Operationally the important number is the tracing cost**: a live trace listener costs 3.3× time and
**7.6× allocations** per hit. Metrics alone cost ~18 ns and **no** extra allocation. Teams should run
metrics always and sample traces.

One known regression, previously accepted by the package owner: telemetry-off hit is ~15% slower than
the pre-v3 baseline, buying guards that are now genuinely enforced. The shipping default
configuration (metrics on) is materially *faster* than v2.

On the cold-start finding: `CachingStartupService` deliberately does not block on the connection so a
pod can become ready while Redis is starting. The related defaults pairing — `ConnectTimeout` 5 s

shipped default and the rule would reject every consumer's out-of-the-box configuration. It is
documented instead.

## 19a. Follow-up attempted after this review — one recommendation withdrawn

§10 recommended making an L2-unavailable read observable by recording an error when a distributed
read is abandoned. **That was implemented, tested, and reverted. It does not work, and the reason is
worth recording so nobody tries it again.**

What was tried: recording `caching.net.errors{layer=redis}` from `InstrumentedDistributedCache`'s
catch blocks, before the activity null-check so tracing-off callers still counted.

Why it failed, in order of discovery:

1. The first test — one read against an **unreachable** endpoint — passed **with the change mutated
   out**, so it proved nothing. `RedisConnectionProvider` already records a Redis error when the
   connection itself fails, which covers that case with or without the decorator.
2. Retargeted at the real gap — a **healthy** endpoint, where the connection eventually succeeds so no
   connection error is ever raised — the test **failed with the fix applied**: one miss was observed
   in the connect window and `caching.net.errors` never appeared at all.

The reason is structural. **A read abandoned during connection establishment does not throw at the
`IDistributedCache` boundary — it returns null**, indistinguishable from a genuine miss. No `catch`
in a decorator can observe it, so no decorator-level counter can ever fix this. The change was also
at risk of double-counting connection failures against `RedisConnectionProvider`, violating the
one-producer rule.

Closing this properly needs a different mechanism — most plausibly consulting the multiplexer's
connection state where the miss is decided, which couples the read path to connection state and
deserves its own design. **It is not a v3.0.0 change.**

No regression test ships for the window either: it closes once the connection is warm, so a test for
it passed in isolation and failed in the full chaos suite depending on execution order. It is
documented in README §28 and `docs/OPERATIONS.md` from hand measurements instead.

**Net effect on this review's verdict: none.** The gap was already recorded as a residual risk in
§16; it is now known to be structural rather than an oversight.

## 20. FINAL RECOMMENDATION

1. **Is v3.0.0 safe for production?** Yes, with the known risks in §16 — principally that a memory
   soak was not run, so begin with a canary.
2. **Are all three modes production-ready?** Yes. All three validated from the real package.
3. **Is Redis behaviour correctly understood and documented?** Yes — `SetSkipMemoryCache(true)`,
   memory locker retained, Redis authoritative, matching the docs.
4. **Is Hybrid L1/L2 behaviour proven?** Yes — L2 read then L1 service, demonstrated across two pods.
5. **Is multi-pod invalidation proven?** Yes — `Remove` and `RemoveByTag` across two live pods, plus a
   cross-process suite.
6. **Is stampede behaviour understood?** Yes — **process-local**. 100 concurrent → 1 factory in-process;
   N pods → up to N. Must not be described as distributed.
7. **Is fail-safe safe?** Yes; stale lifetime is bounded by `FailSafeMaxDuration`.
8. **Is Redis connection management correct?** Yes — one multiplexer per cache, shared by the
   distributed layer and backplane, never per operation, disposed in the correct order.
9. **Is serialization secure?** Yes — no `BinaryFormatter`, no polymorphic type metadata, bounded
   decompression.
10. **Is OpenTelemetry production-safe?** Yes, with tracing sampled rather than always-on.
11. **Is cardinality controlled?** Yes — allow-listed dimensions; keys and tags excluded by default.
12. **Are secrets protected?** Yes — **after** the URI-form fix made in this review.
13. **Is performance acceptable?** Yes. Metrics cost ~18 ns and no allocation; tracing is the
    expensive mode and should be sampled.
14. **Is memory behaviour acceptable?** **NOT VALIDATED.** No soak test was run.
15. **Is the public API maintainable?** Yes — 8 verbs, frozen by an approved-API gate.
16. **Can multiple applications safely consume the package?** Yes.
17. **Can applications share Redis safely?** Yes — proven with three namespaces, no collision, no
    cross-invalidation.
18. **Can an SRE diagnose incidents from telemetry?** Mostly yes — hit rate, miss rate, per-layer
    duration, factory executions and latency, fail-safe, evictions, backplane and serialization are
    all available. **One blind spot:** a cold-start dropped operation logs nothing above `Debug`.
19. **Does the NuGet package work independently?** Yes — 26/26 in a clean room on a purged cache.
20. **Are there ANY reasons not to release today?**
    **Yes — one, and it is procedural rather than a code defect: the branch has never been pushed, so
    CI has never run against this code.** That is exactly how a red CI job survived undetected until
    this review. Push the branch, let CI go green, then tag.

    Two non-blocking recommendations to schedule immediately after: run a memory soak before
    fleet-wide rollout, and add the wildcard-instrumentation warning to `docs/TELEMETRY.md`.
